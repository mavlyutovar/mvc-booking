## 2. Ошибки и перепроверки

### Проблемы в тестах, обнаруженные при ревью

**Проблема 1**: В одном из вариантов теста проверка шагов времени использовала интервалы, которые пересекались между собой (например, бронь с 10:00 до 11:30 и следующая с 10:30 до 12:00). Это приводило к ложным срабатываниям проверки конфликтов.

**Способ обнаружения**: При ручном анализе тестового кода заметил, что `test_it_accepts_start_time_on_15_minute_steps()` создавал брони на последовательные даты (12, 13, 14, 15 ноября), а не на одну дату с пересекающимися интервалами.

**Исправление**: Тесты были переписаны так, чтобы каждый шаг проверялся независимо — бронирования создаются на разные дни или в разных комнатах.

---

**Проблема 2**: В первоначальном варианте вспомогательного метода теста списка бронирований использовались `date()` и `strtotime()`. Это приводило к проблемам с часовыми поясами.

**Способ обнаружения**: При анализе кода тестов заметил смешение стилей — в некоторых местах CarbonImmutable, в других date().

**Исправление**: Все даты в тестах заменены на CarbonImmutable для единообразия и корректной работы с timezone.

---

### Проверки исходного кода (подтверждено через Git history)

| Проблема | Статус проверки | Как обнаружено |
|----------|-----------------|-----------------|
| **SQL-инъекция** в `store()` | ✅ Исправлено | При анализе `BookingController@store()` увидел интерполяцию `$request->room_id` и строк времени. Исправлено через Eloquent + параметризованные запросы внутри транзакции репозитория. |
| **Гонка при конкурентном бронировании** | ✅ Исправлено | В `BookingRepository::findRoomForUpdate()` используется `lockForUpdate()`. Проверил, что блокировка применяется до проверки конфликтов и создания брони. |
| **Проблемы авторизации** на удаление | ✅ Исправлено | В `BookingService::cancel()` есть проверка `$booking->user_id === auth()->user()->id` с выбросом `AuthorizationException`. Тест подтверждает: другой пользователь получает 403 Forbidden. |
| **Ошибки логирования** через `withContext()` | ✅ Исправлено | Контекст не передаётся в следующий вызов — исправлено на прямую передачу параметров в `Log::channel('bookings')->info()`. |

## 3. Что проверял вручную

### Выполненные проверки:

1. **Структуру моделей и связей**:
   - Прочитал модели Booking, Room, Office, User;
   - Проверил связи через Tinker: `Room::first()->bookings`, `User::all()`, `Booking::all()`;

2. **SQL-условия пересечения интервалов**:
   - В `BookingRepository::hasConflict()` условие `$room->bookings()->where('starts_at', '<', $endsAt)->where('ends_at', '>', $startsAt)->exists()` корректно разрешает встречи «впритык»;

3. **Маршруты через route:list**:
   - `GET /api/bookings` — список броней;
   - `POST /api/bookings` — создание;
   - `DELETE /api/bookings/{id}` — отмена;
   - `GET /api/rooms/{room}/bookings/today` — брони на сегодня;

4. **Соответствие бизнес-правилам**:
   - Длительность 15 мин–4 ч через `BookingTimeValidator`;
   - Шаг времени кратен 15 минутам;
   - Рабочие часы офиса 09:00–20:00 по локальному времени;

5. **Конфигурацию канала логирования**:
   - Канал `bookings` существует в `config/logging.php`;

6. **Часовые пояса**:
   - Москва (`Europe/Moscow`, UTC+3), Новосибирск (`Asia/Novosibirsk`, UTC+7);
   - Время клиента переводится через `$startsAt->setTimezone($timezone)`;

7. **Авторизацию**:
   - Тест `test_another_user_cannot_cancel_booking()` подтверждает: 403 Forbidden для чужой брони;

8. **Фактические HTTP-ответы**:
   - Без токена — 401 Unauthorized;
   - С валидными данными — 201 Created;
   - При конфликте — 422 Unprocessable Content с сообщениями на русском;

9. **Запуск тестов**:
   - `docker compose exec app php artisan test --compact` — все 51 тест проходят успешно.

### Непроверенные аспекты:

- Производительность при большом количестве броней (>1000);
- Поведение при отключении БД в середине транзакции;
- Локализация ошибок для разных языков интерфейса.

## 4. Архитектура решения

### Ответственность классов:

```
┌─────────────────────────────────────┐
│      BookingController              │ ← HTTP-слой, авторизованный пользователь
│   - index()                         │   делегирует сервису
│   - store(StoreBookingRequest)       │
│   - destroy(User, int $id)           │
│   - today(Room)                     │ ← существующий метод без изменений
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│      BookingService                 │ ← Координирует создание/отмену брони:
│  - getForUser()                     │   • блокировка комнаты (lockForUpdate)
│  - create(User, Room, time)         │   • валидация времени
│  - cancel(User, int $id)            │   • проверка конфликтов
└─────────────────────────────────────┘
    ↓              ↓
┌──────────────┐ ┌──────────────────────┐
│BookingTimeValidator│ │ BookingRepository │
│- длительность 15 мин–4 ч │ │ - findRoomForUpdate() (lock) │
│- шаг 15 мин   │ │ - hasConflict() (впритык разрешён) │
│- рабочие часы 09:00–20:00│ │ - create() + delete() │
└──────────────┘ └──────────────────────┘
```

### Почему такая архитектура?

1. **BookingTimeValidator** — только бизнес-правила времени, не знает о БД;
2. **BookingRepository** — инкапсулирует SQL и блокировки, сервису не нужно знать про `lockForUpdate()`;
3. **BookingService** — управляет транзакцией и последовательностью проверок;
4. **BookingController** — тонкий слой HTTP-контракта (кроме метода `today()`, который содержит запрос к модели).

## 5. Что не было доверено ИИ

Проверялось независимо:

1. **Соответствие ТЗ**: сопоставил каждый метод контроллера с требованиями задания;

5. **Схема PostgreSQL**: сначала смотрел существующую схему через Tinker перед изменениями;
6. **Авторизацию**: запускал тесты с разными токенами и проверял HTTP-ответы;
7. **Фактический запуск тестов**: `docker compose exec app php artisan test` — 51/51 проходят.
